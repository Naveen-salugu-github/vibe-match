Question 1

What is the Projection Table?

There is no single table called "the projection table." The pipeline produces two distinct output types depending on the use case:

wkly_TRx_proj  Primary Output

Created by: 07.TRx Equivalence for SOB

The final projected TRx volume — how many equivalent treatment units (Benlysta IV, Benlysta SC, Saphnelo) were dispensed each week at NSP-equivalent scale. This is what gets used in SOB dashboards and share calculations.

TRx = DDD_units_eq × SLE_fctr × NSP_Factor_wkly (rounded to nearest integer, per product per week)

Table: us_commercial_catalog_prod.LGU_LUPUS.wkly_TRx_proj

SOB_PROJECTION_FACTOR_*  Scaling Factors

Created by: 01.Projected NBRx Patient Counts

Four factor tables (weekly + monthly × form-level + product-level) that answer: "For every 1 MG of drug observed in eLAAD claims, how many MG were actually sold in the market (DDD)?" Used to scale eLAAD patient counts to total market size.

PROJ_FACTOR = rolling_avg(DDD_SLE_MG) / rolling_avg(LAAD_MG) Weekly = 5-week rolling average Monthly = 3-month rolling average

4 tables: SOB_PROJECTION_FACTOR_WEEKLY, _TOT_WEEKLY, _MONTHLY, _TOT_MONTHLY

Key difference between the two
wkly_TRx_proj applies both the SLE factor and the NSP factor to get actual projected TRx numbers. The SOB_PROJECTION_FACTOR_* tables apply only the SLE factor to the DDD/LAAD ratio — the NSP factor is NOT included in those factors. See Issue #3 for the implication.

Question 4

Gaps and Issues Found

[CRITICAL — Issue 1] NBRX_MTHLY_WKLY_PROJ: origin unknown and pipeline is disconnected

This is the most important issue in the entire pipeline.

  • 03.SLE_NSP_Factors creates NSP_wkly_fact with column week and also refreshes sle_fctr_wkly_eLAAD.NSP_Factor_wkly.
  • 07.TRx Equivalence for SOB reads NSP factors from NBRX_MTHLY_WKLY_PROJ with column Week_Mnth_dt.
  • These are two different tables with different column names. NBRX_MTHLY_WKLY_PROJ is not created by any of the shared scripts.
  • Consequence: When 03.SLE_NSP_Factors runs and updates NSP factors, those updates never reach 07.TRx. The wkly_TRx_proj is computed using potentially stale NSP factors from an unknown source.
  • Action required: Identify which notebook creates NBRX_MTHLY_WKLY_PROJ. Then either (a) update 07.TRx to read from NSP_wkly_fact (rename column in SQL), or (b) make 03.SLE_NSP_Factors also write to NBRX_MTHLY_WKLY_PROJ under the expected schema.
[CRITICAL — Issue 2] NSP factor is excluded from the SOB_PROJECTION_FACTOR calculation

sle_fctr_wkly_eLAAD has two factor columns: SLE_fctr and NSP_Factor_wkly. In 01.Projected NBRx, the projection factor computation only reads SLE_fctr:

SELECT week_end, product_name, IV_SC_Cat AS product_form, SLE_fctr FROM sle_fctr_wkly_eLAAD

The NSP_Factor_wkly column in sle_fctr_wkly_eLAAD is never used in any projection factor computation.

Consequence: SOB_PROJECTION_FACTOR_WEEKLY = rolling(DDD × SLE_fctr) / rolling(LAAD_MG) — this ratio is in DDD-scale, not NSP-scale. If downstream consumers multiply eLAAD patient counts by this factor expecting NSP-scale projections, they will be off by the NSP/DDD ratio. The 07.TRx pipeline avoids this by applying NSP factor directly to DDD before computing TRx. Clarify with team lead whether this is intentional design.

[HIGH — Issue 3] mnthly_TRx_proj never saved to a permanent table

The monthly TRx projection is computed in 07.TRx as NSP_Units_grouped (alias mnthly_Trx) but is only a Spark temporary view — it is never written to a Delta table. Only wkly_TRx_proj is persisted.

Any dashboard or downstream process expecting monthly TRx projection data will find no permanent table. This should either be explicitly saved (.write.format("delta").saveAsTable("LGU_LUPUS.mnthly_TRx_proj")) or documented as intentionally transient.

[MEDIUM — Issue 4] Duplicate union doubles Benlysta historical NSP data (masked bug)

In 07.TRx Equivalence for SOB (line ~319):

comp_nsp = ben_nsp.union(latest_nsp).union(latest_nsp).distinct()

latest_nsp is unioned twice. The .distinct() at the end removes the duplicates, so the final output is correct. However, this doubles the intermediate dataset size before deduplication, wasting Spark resources. More critically, if .distinct() is ever removed (e.g., during a refactor), Saphnelo and Benlysta volumes will double, corrupting the monthly TRx projection. Should be fixed to a single .union(latest_nsp).

[LOW — Issue 5] Two separate 445 calendar sources — risk of divergence
  • 03.SLE_NSP_Factors uses kxwj051_445_calendar (Unity Catalog, managed)
  • 01.Projected NBRx Patient Counts uses DDD 445 Calendar.csv (static S3 file at s3://az-us-lg-pilot-user/hive/lgu_lupus/...)

These are the same calendar but maintained separately. If the fiscal year rolls over and the Unity Catalog table is updated but the S3 CSV is not (or vice versa), week-to-month mappings will differ between the two pipelines, causing inconsistent monthly aggregations. Recommendation: Consolidate 01.Projected NBRx to use the Unity Catalog table.

Open Questions from Excel (Book1.xlsx annotations)
  • "What should be used as recent factor to fill NSP missing gaps?" — Current code uses the factor from MAX(yr_mnth) in Table31 (the single most recent computed month). All future missing months get this same value. If the factor is trending, this will introduce bias. Consider using a 3-month rolling average of computed factors instead.
  • "When is NSP missing? What's the lag?" — Not explicitly documented in the code. IQVIA NSP data typically lags 4–6 weeks, meaning the most recent 1–2 months in the DDD data will not have a matching NSP factor and will be filled. The code handles this silently without logging which months were filled or from which source month.
  • "Cross check with leads for standardization" (Nov-2024 adjustment) — Verified: correctly implemented as units_eq / 0.8 only for yr_mnth = '2024-11'.
  • "Check calendar creation" — Calendar is correctly built from kxwj051_445_calendar in 03.SLE_NSP_Factors. But see Issue #5 regarding the duplicate S3 calendar in 01.Projected NBRx.
